## Critical Blockers (must fix before first deploy)

### 1. `JWT_SECRET` has no safe default — the app will refuse to start

`application.yml` has `secret: ${JWT_SECRET}` with **no fallback**. If the environment variable is not set, Spring Boot throws `IllegalArgumentException` at startup.

**Action:**
```bash
# Generate a secure 64-character hex secret
openssl rand -hex 32
```
Add it to your deployment environment as `JWT_SECRET=<output>`. Never commit it to git. Use your platform's secrets manager (Railway Variables, Render Secret Files, AWS Secrets Manager, etc.).

---

### 2. CORS will block the frontend in production

`CORS_ALLOWED_ORIGINS` defaults to `http://localhost:5173`. In production the browser will get blocked with a CORS error.

**Action:** Set this variable to your actual domain:
```
CORS_ALLOWED_ORIGINS=https://app.yourdomain.com
```

---

### 3. `VITE_API_URL` and `FRONTEND_BASE_URL` point to localhost

The frontend calls `http://localhost:8080` by default. QR codes generated by the backend will point to `http://localhost:5173`.

**Action:** Set both at build/runtime:
```
VITE_API_URL=https://api.yourdomain.com          # Passed as Docker build-arg
FRONTEND_BASE_URL=https://app.yourdomain.com      # Backend env var
```

---

### 4. SMS, Email, and Payment providers are on `mock` — nothing will send

All three external gateways default to `mock` mode:
- `SMS_PROVIDER=mock` → OTP login will silently succeed but no SMS is sent
- `EMAIL_PROVIDER=mock` → No confirmation emails
- `PAYMENT_PROVIDER=mock` → Payments always succeed without charging anyone

**Action:** Choose and configure at least one real provider per service:

| Service | Recommended Provider | Required Variables |
|---|---|---|
| SMS / OTP | MSG91 | `SMS_PROVIDER=msg91`, `MSG91_AUTH_KEY`, `MSG91_TEMPLATE_ID` |
| Email | Any SMTP (Gmail, SendGrid, Mailgun) | `EMAIL_PROVIDER=smtp`, `MAIL_HOST`, `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD` |
| Payments | Razorpay | `PAYMENT_PROVIDER=razorpay`, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `PAYMENT_WEBHOOK_SHARED_SECRET` |

---

### 5. No TLS — all traffic is unencrypted HTTP

The `edge-proxy` (Nginx TLS terminator) is in a Docker Compose `profile: [tls]` and is **disabled by default**. Sending JWT tokens and customer data over plain HTTP is a security failure.

**Action:** Either:
- **Option A (Managed — recommended):** Deploy behind a platform that handles TLS automatically (Railway, Render, Fly.io, AWS ALB). Set `VITE_API_URL` to the HTTPS URL.
- **Option B (Self-managed VPS):** Provision a cert with Certbot, place keys in `docker/certs/`, and start the stack with `--profile tls`:
  ```bash
  docker compose --profile tls up -d
  ```

---

### 6. Monitoring config files may be missing

`docker-compose.yml` mounts `./monitoring/prometheus.yml`, `./monitoring/alerts.yml`, and `./monitoring/grafana/provisioning/**`. If these files don't exist on the host, the Prometheus and Grafana containers will fail to start.

**Action:** Verify the monitoring directory exists and contains valid configs. At minimum:

```yaml
# monitoring/prometheus.yml
global:
  scrape_interval: 15s
scrape_configs:
  - job_name: dineops-backend
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ['backend:8080']
```

## Deployment Steps (once all blockers are cleared)

### Step 1 — Prepare secrets

```bash
# Generate JWT secret
openssl rand -hex 32

# Generate strong DB and Redis passwords
openssl rand -base64 24
```

Create a `.env` file on your server (do NOT commit it to git) by copying `.env.production.example` and filling in every `replace_with_*` placeholder.

### Step 2 — Clone and configure

```bash
git clone https://github.com/your-org/dineops.git
cd dineops
cp .env.production.example .env
nano .env   # fill in all values
```

### Step 2.5 — Run preflight checks

```bash
# Linux/macOS
bash scripts/preflight-deploy.sh .env

# Windows PowerShell
powershell -ExecutionPolicy Bypass -File scripts/preflight-deploy.ps1 -EnvFile .env
```

### Step 3 — Create monitoring configs

```bash
mkdir -p monitoring/grafana/provisioning/datasources monitoring/grafana/provisioning/dashboards monitoring/grafana/dashboards

cat > monitoring/prometheus.yml << 'EOF'
global:
  scrape_interval: 15s
  evaluation_interval: 15s
scrape_configs:
  - job_name: dineops-backend
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ['backend:8080']
EOF

echo "groups: []" > monitoring/alerts.yml
```

### Step 4 — Build and launch

```bash
# Without TLS (behind managed platform)
docker compose up -d --build

# With self-managed TLS (VPS + Certbot certs in docker/certs/)
docker compose --profile tls up -d --build
```

### Step 5 — Verify health

```bash
# Backend health
curl https://api.yourdomain.com/actuator/health

# Database migrations applied
docker compose logs backend | grep -i flyway

# All containers running
docker compose ps
```

### Step 6 — Seed the first super admin

The app has no built-in seed script. Register the first user via the API, then manually promote them to `SUPER_ADMIN` in the database:

```sql
UPDATE users
SET role = 'SUPER_ADMIN'
WHERE email = 'your-admin@example.com';
```

### Step 7 — Smoke test end-to-end

1. Open `https://app.yourdomain.com` — landing page loads
2. Register as a restaurant owner → OTP SMS arrives → dashboard loads
3. Create a menu category and item
4. Generate a QR code for a table → scan it → public menu appears
5. Place an order → kitchen display shows it → status updates in real time
6. Check `https://app.yourdomain.com/dashboard/closing-report` → daily report renders

### Step 8 — Set up ongoing operations

```bash
# View live logs
docker compose logs -f backend

# Restart a single service without downtime
docker compose up -d --no-deps --build backend

# Backup the database
docker exec dineops-postgres pg_dump -U $POSTGRES_USER $POSTGRES_DB > backup.sql

# Update to a new version
git pull && docker compose up -d --build
```

## Recommended Managed Hosting (fastest path)

| Platform | Notes |
|---|---|
| **Railway** | Postgres + Redis add-ons available; auto TLS; environment variables UI. Best for solo devs. |
| **Render** | Free tier available; managed Postgres; auto-deploy from GitHub. |
| **Fly.io** | Good for Docker deploys; persistent volumes for Postgres. |
| **AWS (EC2 + RDS + ElastiCache)** | Most control; most setup work; recommended when you have 50+ tenants. |

For Railway specifically, the entire stack can be running in under 30 minutes:
1. Create a new project → "Deploy from GitHub repo"
2. Add a PostgreSQL plugin and a Redis plugin
3. Copy connection strings into environment variables
4. Set `JWT_SECRET`, `CORS_ALLOWED_ORIGINS`, `VITE_API_URL`, `FRONTEND_BASE_URL`
5. Deploy
